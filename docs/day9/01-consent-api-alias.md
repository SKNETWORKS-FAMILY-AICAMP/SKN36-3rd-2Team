## 2. 작업 배경

프론트엔드에서는 사건의 주요 증거와 정답이 소스코드에
노출되지 않도록 스포일러 검사 정책을 적용하고 있다.

기존 동의 API는 주소에 보호 증거 ID가 포함되어 있어
프론트엔드 스포일러 검사와 충돌하는 문제가 발생하였다.

프론트엔드에서 증거 ID가 없는 동의 API를 호출하고 있었으나,
해당 경로가 백엔드에 등록되지 않아 HTTP 404가 발생하였다.

이번 작업에서는 기존 동의 처리 로직을 변경하지 않고
동일한 기능을 수행하는 신규 API 경로를 추가하였다.

## 3. 작업 목적

- 프론트엔드 동의 API 호출 오류 해결
- 스포일러 검사 정책과의 충돌 방지
- 기존 API 하위 호환성 유지
- 동의 처리 로직 중복 방지
- 서버 상태 무결성 유지
- Django 독립 콘텐츠 승인 정책 유지
- 보호 증거 및 엔딩 정보 노출 방지

## 4. API 변경 사항

| 구분 | HTTP 메서드 | API 경로 |
|---|---|---|
| 신규 권장 API | POST | /api/games/{session_id}/consent |
| 기존 호환 API | POST | /api/games/{session_id}/evidence/E30/consent |

두 API는 동일한 submit_e30_consent 함수를 사용한다.

신규 API를 위해 별도의 비즈니스 로직을 작성하지 않았으며,
기존 동의 처리 함수에 새로운 경로만 추가하였다.

## 5. 요청 및 응답 명세

### 5.1 요청 형식

    {
      "expectedRevision": 12,
      "consent": true
    }

| 필드 | 자료형 | 필수 여부 | 설명 |
|---|---|---|---|
| expectedRevision | 정수 | 필수 | 최신 게임 상태 버전 |
| consent | 불리언 | 필수 | 플레이어의 명시적 동의 |

consent에는 불리언 true만 허용한다.

문자열, 숫자, null 및 false는 유효한 동의로 처리하지 않는다.

### 5.2 응답 형식

정상 처리 시 HTTP 200과 기존 GameResponse를 반환한다.

| 필드 | 자료형 | 설명 |
|---|---|---|
| e30ConsentAvailable | 불리언 | 현재 동의 가능 여부 |
| e30ConsentGranted | 불리언 | 플레이어 동의 저장 여부 |
| revision | 정수 | 현재 게임 상태 버전 |

기존 GameResponse의 필드는 삭제하거나 변경하지 않았다.

### 5.3 캐시 정책

    Cache-Control: private, no-store

동의 응답이 공유 캐시에 저장되지 않도록
기존 캐시 방지 정책을 유지한다.

신규 API와 기존 API는 동일한 처리 흐름을 사용한다.

따라서 신규 경로 추가에 따른 별도 권한 정책이나
데이터 저장 구조 변경은 발생하지 않는다.

## 7. HTTP 응답 처리

| 상태 코드 | 발생 조건 | 프론트엔드 처리 |
|---|---|---|
| 200 | 정상 동의 또는 중복 동의 | 최신 게임 상태 반영 |
| 404 | 세션 없음 또는 소유권 불일치 | 세션 상태 확인 |
| 409 | 동의 조건 미충족 또는 상태 충돌 | 게임 상태 재조회 |
| 422 | 잘못된 요청 또는 명시적 동의 누락 | 요청 데이터 확인 |

Django 승인 서비스에 장애가 발생하더라도
동의 요청을 임의로 허용하지 않는다.

기존 Fail-closed 보안 정책을 유지한다.

## 8. 게임 상태 관리

### 8.1 최초 동의

최초 동의 요청 시 다음 절차를 수행한다.

1. 세션 소유권 검증
2. expectedRevision 검증
3. 게임 진행 상태 확인
4. 선행 조건 확인
5. Django 콘텐츠 승인 검증
6. 플레이어 동의 기록 저장
7. revision 1 증가
8. 최신 GameResponse 반환

### 8.2 중복 동의

이미 동의한 플레이어가 현재 revision으로 다시 요청하면
기존 승인 및 진행 조건을 재검증한 후 동일한 상태를 반환한다.

중복 요청으로 인해 revision이나 증거 점수가
추가로 증가하지 않는다.

### 8.3 교차 호출

다음 두 가지 호출 순서를 검증 대상으로 설정하였다.

- 신규 API 호출 후 기존 API 호출
- 기존 API 호출 후 신규 API 호출

두 API는 동일한 SQLite 게임 상태를 공유한다.

이전 revision을 사용하는 요청은 HTTP 409로 차단한다.

## 9. 보호 상태 관리

플레이어 동의만으로 다음 상태가 변경되어서는 안 된다.

- 획득 증거
- 증거 수집 점수
- 게임 진행 플래그
- 문서 열람 권한
- 스토리 이벤트 대기열
- 남은 범인 지목 횟수
- 게임 결과
- 엔딩 코드

플레이어 동의는 보호 콘텐츠 공개 승인이나
스토리상 당사자의 동의 및 안전 검증을 의미하지 않는다.

동의만으로 E30 증거를 지급하거나 DEEP 엔딩을
활성화하지 않는다.

## 13. 프론트엔드 연동 방법

프론트엔드에서는 신규 동의 API를 사용한다.

    POST /api/games/{session_id}/consent

### 연동 순서

1. 현재 게임 상태를 조회한다.
2. e30ConsentAvailable 값을 확인한다.
3. 동의 가능한 상태인 경우 동의 UI를 표시한다.
4. 플레이어가 명시적으로 동의하면 API를 호출한다.
5. 최신 expectedRevision과 consent=true를 전달한다.
6. 반환된 GameResponse로 게임 상태를 갱신한다.
7. e30ConsentGranted로 동의 저장 여부를 확인한다.
8. HTTP 409 발생 시 최신 게임 상태를 다시 조회한다.

기존 세션 소유권 확인용 쿠키를 함께 전달해야 한다.

동의 여부와 증거 획득 여부는 별도로 처리해야 하며,
동의 완료만으로 보호 증거 또는 DEEP 엔딩 UI를
활성화해서는 안 된다.
