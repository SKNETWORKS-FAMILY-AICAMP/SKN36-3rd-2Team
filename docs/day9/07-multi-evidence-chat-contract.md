이번 작업에서는 복수 증거 제시 기능의 요청 및
응답 계약과 내부 처리 구조를 설계한다.

실제 운영 코드 구현은 후속 개발 단계에서 진행한다.

## 2. 작업 배경

기존 NPC 대화 API는 presentedEvidenceId 필드를
사용하여 증거 1개를 제시할 수 있다.

프론트엔드는 복수 증거 선택 기능을 갖추고 있으나
서버의 단일 증거 처리 제한으로 인해 증거 2개를
선택한 경우 요청을 차단하고 있다.

프론트엔드 요구사항에 따라 기존 단일 증거 요청을
유지하면서 최대 2개의 증거를 동시에 제시하는
기능을 추가할 예정이다.

Agent 계약과 내부 대화 처리까지 확장해야 한다.

## 4. 핵심 요구사항

- 일반 NPC 대화 유지
- 기존 presentedEvidenceId 단일 증거 요청 유지
- evidenceIds 배열 형태의 복수 증거 요청 추가
- 한 번에 최대 2개 증거 제시
- 플레이어 추가 의견 note 지원
- 동일 증거 중복 전달 금지
- 미수집 증거 제시 금지
- NPC 접근 및 정보 공개 정책 유지
- NPC 응답은 한 번만 생성
- 대화 기록과 게임 상태를 원자적으로 저장
- 기존 ChatResponse 구조 유지

## 5. HTTP API 계약

    POST /api/games/{session_id}/chat

기존 세션 소유권 쿠키를 사용한다.

현재 선택 NPC는 서버에 저장된 선택 상태를 기준으로
결정하며 요청 본문에서 임의로 지정하지 않는다.

### 5.1 일반 대화

    {
      "question": "사건 당시 어디에 계셨나요?"
    }

### 5.2 기존 단일 증거 제시

    {
      "question": "이 자료에 대해 설명해 주세요.",
      "presentedEvidenceId": "E11"
    }

### 5.3 배열을 사용하는 단일 증거 제시

    {
      "question": "이 자료에 대해 설명해 주세요.",
      "evidenceIds": ["E11"]
    }

### 5.4 복수 증거 제시

    {
      "question": "두 자료의 내용이 다른 이유가 무엇인가요?",
      "evidenceIds": ["E11", "E12"],
      "note": "두 기록의 내용이 일치하지 않습니다."
    }

예시에 사용된 증거 식별자는 내부 개발용 예시이다.

실제 요청에는 서버에서 획득을 확인한 증거만
전달해야 한다.

## 6. 요청 필드 명세

| 필드 | 자료형 | 필수 | 제약 조건 |
|---|---|---|---|
| question | string | 예 | 1~200자, 공백만 입력 금지 |
| presentedEvidenceId | string 또는 null | 아니오 | 기존 단일 증거 |
| evidenceIds | string 배열 | 아니오 | 1~2개, 중복 금지 |
| note | string 또는 null | 아니오 | 최대 200자 |

question의 기존 최대 길이를 유지한다.

note는 제시 증거와 함께 전달하는 플레이어 의견이다.

note는 공백을 정리하며 빈 문자열은 추가 의견이
없는 상태로 처리한다.

note가 증거 획득 조건이나 서버 검증 플래그를
직접 변경해서는 안 된다.

note를 서버 지시문이나 사실 근거로 취급하지 않는다.

내부 프롬프트에서는 승인된 근거와 플레이어 의견을
명확하게 구분해야 한다.

## 7. 요청 정규화 규칙

| 요청 형태 | 정규화 결과 |
|---|---|
| 증거 미지정 | 빈 내부 증거 목록 |
| presentedEvidenceId 단일 값 | 증거 1개 목록 |
| evidenceIds 길이 1 | 증거 1개 목록 |
| evidenceIds 길이 2 | 증거 2개 목록 |

내부 Agent 계약에서는 정규화된 불변 증거 목록을
사용하는 방향으로 구현한다.

외부 요청의 evidenceIds 빈 배열은 허용하지 않는다.

presentedEvidenceId와 evidenceIds가 모두 실제
값으로 지정된 요청은 모호하므로 거부한다.

presentedEvidenceId가 null인 경우는 기존 호환성을
위해 허용한다.

유효한 note가 있으나 제시 증거가 없는 요청은
허용하지 않는다.

사용자가 선택한 증거 순서는 표시 및 대화 문맥에
유지한다.

권한 검사 결과는 입력 순서에 따라 달라지지 않아야 한다.

## 8. 요청 검증 및 오류 응답

| 조건 | 상태 코드 |
|---|---|
| 정상 요청 | 200 |
| 미수집 증거 제시 | 403 |
| 보호 증거 또는 복수 제시 권한 위반 | 403 |
| 다른 세션 접근 | 404 |
| 게임 상태 경쟁 또는 선택 상태 불일치 | 409 |
| 증거 개수 및 형식 오류 | 422 |
| 동일 증거 중복 입력 | 422 |
| 증거 필드 충돌 | 422 |
| 길이 제한 위반 | 422 |
| NPC 응답 형식 오류 | 502 |
| 대화 또는 콘텐츠 서비스 장애 | 503 |
| 처리 시간 초과 | 504 |

기존 API의 예외 처리 계약을 유지한다.

미공개 증거 이름이나 내부 정책 식별자를
오류 응답에 포함하지 않는다.

기존 콘텐츠 버전에서는 E01~E10만 허용한다.

확장판은 버전에 등록된 증거 카탈로그를 기준으로
검증하며 E26과 E30의 기존 보호 정책을 유지한다.

## 9. NPC 증거 제시 권한

증거 수집 여부와 NPC에게 제시할 수 있는 권한은
서로 다른 조건이다.

현재 단일 증거 구현에서는 정식 제시 대상이 아닌
NPC에게 수집 증거의 이름을 언급하는 일반 질문과
정식 제시 이력 생성을 구분한다.

기존 단일 증거 경로의 동작을 변경하지 않는다.

신규 복수 증거 경로에서는 두 증거의 정식 제시
권한을 각각 검증한다.

복수 증거 중 하나라도 정식 제시가 허용되지 않는 경우
전체 복수 제시 요청을 거부하는 정책을 제안한다.

권한이 없는 증거를 무시하고 나머지 증거만 처리하는
부분 성공 방식은 사용하지 않는다.

이 정책은 구현 전 콘텐츠 담당자와 확인한다.

## 10. 보호 증거 처리

E26 및 E30은 기존 일반 증거 제시 컨텍스트에서
보호 대상으로 취급되고 있다.

이번 복수 증거 기능을 이유로 기존 보호 조건을
완화하지 않는다.

초기 복수 증거 구현에서는 E26 및 E30을 포함한
복수 제시 요청을 차단한다.

기존 보호 증거의 별도 조회 및 추론 정책은 유지한다.

추후 별도의 검토와 승인 없이 일반 증거와 동일한
복수 제시 경로에 포함하지 않는다.

          |

증거마다 독립적인 권한 검증을 수행한다.

두 증거가 제시되었다는 사실만으로 두 증거의 관계,
NPC의 거짓말, 범행 여부 또는 모순을 확정하지 않는다.

NPC 응답은 현재 승인된 근거에 기반해야 한다.

## 12. 상태 무결성 및 트랜잭션

복수 증거 제시는 하나의 사용자 대화 턴이다.

두 번의 독립적인 대화 실행으로 구현하지 않는다.

다음 상태를 하나의 트랜잭션에서 저장해야 한다.

- NPC별 증거 제시 이력
- 승인된 NPC 진술 단계
- 승인된 대화 트리거
- 실제 인용한 지식 카드 공개 이력
- 승인된 후속 증거 획득 상태
- 스토리 이벤트 대기열
- NPC 대화 기록
- 최신 GameState 및 NPC 선택 Revision

증거 검증, 대화 생성 또는 이벤트 승인에 실패하면
중간 상태를 저장하지 않는다.

기존 repository.commit_turn의 원자적 저장 구조를
재사용하는 방향으로 구현한다.

내부 상태 변경에 따른 Revision 증가량은 기존 대화
엔진의 규칙을 유지한다.

한 번의 트랜잭션 저장과 Revision 증가량은
동일한 개념이 아니다.

최종 응답의 Revision은 실제 저장된 상태와 일치해야 한다.

대화 시작 이후 선택 NPC 또는 게임 상태가 변경된
경우 이전 컨텍스트로 저장해서는 안 된다.

## 13. RAG 및 Agent 보안

- 기존 PolicyEvaluator 재사용
- 현재 세션의 실제 수집 증거 확인
- NPC별 승인된 정보 공개 범위 유지
- 기존 Dense, BM25, Graph 및 RRF 구조 유지
- 두 증거에 관한 승인된 근거만 사용
- 플레이어 note를 신뢰 근거로 사용 금지
- 비공개 지식 카드 및 문서 노출 금지
- 보호 증거의 별도 접근 정책 유지
- 허용되지 않은 추론 및 자동 자백 생성 금지
- 실제 인용된 승인 근거만 공개 처리

복수 증거의 제시 사실과 RAG 문서 접근 권한을
동일한 개념으로 취급하지 않는다.

임시 상태에서 두 증거의 제시 조건이 충족되더라도
기존 접근 정책에 명시된 정보만 검색 및 공개한다.

## 14. 응답 계약

기존 ChatResponse의 필드를 유지한다.

| 필드 | 자료형 | 설명 |
|---|---|---|
| characterId | string | 응답 NPC |
| display_text | string | 표시용 NPC 응답 |
| game | GameResponse | 최신 게임 상태 |

응답에는 단일 NPC 응답과 최신 게임 상태를
포함한다.

note는 기존 대화 요청의 일부로 취급하되
대화 이력 표시 시 기존 응답 형식과 호환되도록 한다.

내부 LLM 프롬프트, 비공개 정책 정보 및 원본 검색
컨텍스트는 응답하지 않는다.

## 15. 진행 이벤트

기존 GameResponse.events 구조를 유지한다.

| 이벤트 | 처리 기준 |
|---|---|
| NPC_REPLIED | 정상 NPC 응답 시 1개 |
| EVIDENCE_PRESENTED | 최초로 정식 제시한 증거마다 1개 |
| KNOWLEDGE_UPDATED | 실제 신규 지식 공개 발생 |
| GAME_PROGRESS_UPDATED | 실제 서버 진행 조건 변경 |

이미 제시한 증거는 신규 제시 이벤트를 발생시키지 않는다.

두 증거 중 하나만 최초 제시인 경우 해당 증거의
신규 제시 이벤트만 반환한다.

스토리 이벤트는 기존 pending 및 ACK API를 유지한다.

## 16. 중복 요청 처리

동일 증거의 제시 이력은 중복 생성하지 않는다.

동일한 두 증거를 다시 보여주더라도 신규 질문에 대한
NPC 대화 자체는 허용할 수 있다.

중복 증거 제시의 멱등성과 전체 대화 요청의 멱등성을
구분한다.

현재 API에는 요청별 Idempotency-Key가 없으므로
네트워크 재시도에 대한 완전한 대화 중복 방지를
보장하지 않는다.

## 17. 기존 콘텐츠 및 API 호환성

기존 일반 대화 및 단일 증거 대화 요청을 유지한다.

기존 presentedEvidenceId 필드를 삭제하지 않는다.

기존 응답 필드와 자료형을 변경하지 않는다.

기존 Agent 계약을 사용하는 호출부가 깨지지 않도록
내부 배열 필드는 기본값과 정규화 계층을 사용한다.

확장판 전용 복수 증거 동작은 기존 콘텐츠 버전과
명시적으로 구분한다.

이번 계약에서는 기존 콘텐츠의 복수 증거 동작을
새로 보장하지 않는다.

## 18. 프론트엔드 연동

변경 예상 파일:

    frontend/src/api/httpApi.ts

기존 presentEvidence 함수는 evidenceIds 배열을
인자로 받고 있으므로 인터페이스 변경을 최소화한다.

신규 백엔드 구현 및 dev 병합 완료 후 최대 증거 수를
1에서 2로 변경한다.

요청 예시:

    post({
      question,
      evidenceIds,
      note: note?.trim() || null,
    })

신규 필드가 지원되지 않는 기존 서버에는 기존 요청
형식을 사용해야 한다.

단일 증거 요청은 기존 presentedEvidenceId 방식도
계속 지원한다.

서버 구현 완료 전에는 두 증거 제시 제한을 해제하지 않는다.

기존 NPC 선택 동기화 및 세션별 대화 요청 잠금은
유지한다.
