이번 작업은 플레이어가 발견한 정보를 기반으로
타임라인을 제공하기 위한 설계 작업이다.

실제 운영 코드 및 프론트엔드 코드는 수정하지 않는다.

## 2. 작업 배경

프론트엔드의 타임라인 화면에는 다음 기능이
구현되어 있다.

- 발견 순서 정렬
- 사건 시각 순서 정렬
- 새로 알게 된 항목 표시
- 플레이어의 수동 모순 표시
- 수동 모순 표시의 로컬 저장

현재 서버 GET /timeline API가 연결되지 않아
타임라인 항목은 제공되지 않는다.

플레이어의 실제 조사 결과를 기반으로 공개 가능한
정보만 반환하는 전용 API가 필요하다.

## 3. 기존 코드 분석

| 파일 | 현재 역할 |
|---|---|
| scenario/source_timeline.py | 관리자 전용 원본 타임라인 |
| scenario/timeline_adapter.py | 원본 타임라인의 게임 엔진 변환 |
| scenario/validators/timeline_document_validator.py | 타임라인 메타데이터 검증 |
| scenario/schemas/document.py | 플레이어용 문서 및 접근 조건 |
| scenario/schemas/game_state.py | 게임 진행 및 공개 상태 |
| scenario/investigation_progress.py | 승인된 추론 규칙 |
| trigger/atomic_dialogue.py | GameState 및 대화 기록 저장 |
| frontend/src/screens/Timeline/Timeline.tsx | 타임라인 화면 |
| frontend/src/store/noteStore.ts | 플레이어 수동 모순 표시 |

기존 SourceTimelineEvent의 access_scope는
admin_only로 정의되어 있다.

기존 타임라인 변환 결과는 ENGINE_ONLY 범위이다.

따라서 관리자 원본 타임라인이나 게임 엔진용
타임라인을 그대로 반환해서는 안 된다.

기존 타임라인 어댑터는 인물의 진술과 관리자 정본
사건 정보를 분리하고 있다.

플레이어 타임라인에서도 이 구분을 유지한다.

## 4. 핵심 요구사항

- 실제로 발견한 정보만 표시
- 잠긴 챕터의 정보 노출 방지
- 미수집 증거 정보 노출 방지
- 미공개 NPC 진술 노출 방지
- 발견 순서와 사건 시각 순서 구분
- 신규 발견 항목 표시 지원
- 플레이어 수동 모순 표시 지원
- 서버 검증 모순과 사용자 의심 분리
- 세션 재접속 시 발견 항목 유지
- 기존 증거 및 콘텐츠 접근 정책 유지
- 읽기 전용 API 구성
- 기존 GameResponse 계약 유지

## 5. API 요청 계약

    GET /api/games/{session_id}/timeline

기존 세션 소유권 쿠키를 사용한다.

별도 요청 Body는 필요하지 않다.

전체 타임라인 정답을 요청하는 옵션이나
비공개 콘텐츠 포함 옵션은 제공하지 않는다.

## 6. API 응답 계약

응답 예시:

    {
      "revision": 15,
      "contradictionMarkingAvailable": true,
      "items": [
        {
          "id": "tl_01",
          "occurredAt": null,
          "timeLabel": "21:20",
          "title": "접수 기록 확인",
          "description": "접수 기록에서 방문 사실을 확인했습니다.",
          "chapterId": "CH01",
          "sourceIds": ["E19"],
          "discoveryOrder": 1,
          "discoveredRevision": 5,
          "isContradiction": false
        }
      ]
    }

위 값은 API 구조 설명을 위한 가상 예시이며
실제 사건 정본에 대한 설명이 아니다.

### 6.1 최상위 필드

| 필드 | 자료형 | 설명 |
|---|---|---|
| revision | integer | 서버 게임 상태 Revision |
| contradictionMarkingAvailable | boolean | 수동 모순 표시 기능 사용 가능 여부 |
| items | array | 현재 공개 가능한 타임라인 항목 |

### 6.2 항목 필드

| 필드 | 자료형 | 설명 |
|---|---|---|
| id | string | 세션 내 안정적인 공개 항목 ID |
| occurredAt | string 또는 null | 날짜와 시각이 확인된 사건 발생 시점 |
| timeLabel | string 또는 null | 사용자 표시용 시간 정보 |
| title | string | 공개 가능한 제목 |
| description | string | 공개 가능한 상세 내용 |
| chapterId | string | 발견과 관련된 챕터 |
| sourceIds | string 배열 | 공개 가능한 근거 ID |
| discoveryOrder | integer 또는 null | 실제 발견 순서 |
| discoveredRevision | integer 또는 null | 최초 발견 Revision |
| isContradiction | boolean | 승인된 서버 규칙으로 확인된 모순 |

항목 ID는 동일한 세션 및 동일한 발견 항목에
대해 안정적으로 유지되어야 한다.

관리자 원본 이벤트 ID와 파일 경로를 그대로
외부에 노출하지 않는다.

### 6.3 초기 상태 응답

    {
      "revision": 0,
      "contradictionMarkingAvailable": false,
      "items": []
    }

발견한 항목이 없다면 빈 배열을 반환한다.

비공개 항목에 대한 빈 카드 또는 자리표시자를
생성하지 않는다.

## 7. 타임라인 공개 데이터 분류

### 7.1 증거 기반 항목

실제로 획득한 증거의 승인된 공개 정보를 사용한다.

증거의 존재를 아는 것과 해당 증거를 획득한 것은
서로 다른 상태이다.

미수집 증거는 타임라인에 표시하지 않는다.

### 7.2 NPC 진술 기반 항목

플레이어에게 실제로 공개된 승인된 진술만 사용한다.

NPC가 해금되어 있다는 사실만으로 해당 NPC의
모든 진술을 반환하지 않는다.

기존 disclosed_cards 및 접근 정책을 활용한다.

신분 정보 카드와 사건 관련 유효 진술은 구분한다.

NPC의 진술은 객관적으로 확인된 사건 사실과
구분할 수 있도록 표시 문구를 구성한다.

### 7.3 추론 기반 항목

기존 승인된 추론 규칙과 서버 상태를 활용한다.

증거 조합을 제출했다는 이유만으로 추론이
성립했다고 간주하지 않는다.

검증된 추론만 타임라인에 추가할 수 있다.

모든 추론이 모순을 의미하는 것은 아니다.

### 7.4 제외 대상

- 관리자 전용 원본 사건 정보
- 미수집 증거
- 미공개 NPC 진술
- 미승인 스토리 콘텐츠
- 보호된 문서의 비공개 구획
- 범인 정답 및 미공개 엔딩 정보
- 사용자 질문 또는 note에서 주장한 미검증 사실
- LLM이 생성한 검증되지 않은 사건 정보

## 8. 발견 순서와 사건 시각

두 시간 개념을 구분한다.

| 구분 | 의미 |
|---|---|
| 발견 순서 | 플레이어가 정보를 알게 된 순서 |
| 사건 시각 | 기록 또는 진술에서 확인한 사건 시점 |

API 기본 반환 순서는 발견 순서이다.

discoveryOrder는 세션 내 최초 발견 기준으로
단조 증가하도록 구성한다.

동일 Revision에서 여러 항목이 공개될 수 있으므로
Revision만으로 순서를 결정하지 않는다.

같은 근거에서 여러 항목이 발생할 때에는
서버가 정의한 안정적인 순서로 등록한다.

사건 시각은 승인된 콘텐츠가 제공하는 값만 사용한다.

시간대가 확인되지 않은 경우 임의로 UTC 또는
특정 지역 시간대를 부여하지 않는다.

날짜와 시각이 모두 확인된 경우에만 occurredAt을
ISO 8601 형식으로 구성한다.

시각만 확인된 경우에는 timeLabel을 제공할 수 있다.

정확한 시각을 알 수 없는 경우 null을 반환한다.

2016년과 현재 사건의 시간 정보처럼 서로 다른
날짜의 자료를 단순 시각 문자열만으로 비교하지 않는다.

날짜 없는 항목의 상대적인 시각 순서는 동일 날짜가
확인되는 범위에서만 의미를 부여한다.

정확한 시간순 비교가 불가능한 항목은 시각 순 정렬의
마지막에 배치하고 발견 순서를 유지한다.

프론트에서 발생 시점을 추정하거나 임의의 날짜를
생성하지 않는다.

## 9. 신규 발견 표시 정책

discoveredRevision은 해당 항목이 처음 발견된
시점의 서버 Revision이다.

타임라인을 조회해도 발견 Revision을 변경하지 않는다.

프론트엔드는 이전 타임라인 조회에서 확인한
Revision을 기준으로 신규 표시를 계산할 수 있다.

    isNew = discoveredRevision > lastSeenRevision

lastSeenRevision은 세션 단위로 관리한다.

discoveredRevision이 null인 기존 복원 항목에는
임의의 신규 표시를 적용하지 않는다.

신규 표시 여부는 UI 상태이며 게임 진행이나
증거 접근 권한에 영향을 주지 않는다.

## 10. 모순 표시 정책

### 10.1 서버 검증 모순

isContradiction은 서버가 승인된 규칙과 공개 근거를
기반으로 확인한 모순 여부이다.

단순히 두 진술의 문장이 다르다는 이유로
모순을 자동 확정하지 않는다.

서버에서 승인된 모순 판정 규칙이 확인되지 않았다면
초기 구현의 isContradiction은 false로 유지한다.

false는 모순이 없다는 최종 판정이 아니라
서버에서 확인된 모순이 없다는 의미이다.

### 10.2 플레이어 수동 표시

기존 프론트엔드 noteStore의 marks를 사용한다.

수동 모순 표시는 플레이어 개인의 추리 기록이며
서버에서 검증된 모순 판정과 분리한다.

수동 표시가 다음 정보를 변경해서는 안 된다.

- 게임 진행 플래그
- NPC 진술 단계
- 증거 획득 여부
- 수집 점수
- 지목 가능 여부
- 최종 엔딩 판정

수동 표시 전용 서버 저장 API는 이번 범위에
포함하지 않는다.

### 10.3 기능 공개 조건

스토리 담당자가 확인한 최소 세 사람의 진술
수집 조건을 적용하는 방향으로 설계한다.

contradictionMarkingAvailable은 서로 다른 NPC의
유효한 사건 관련 진술 수를 기준으로 계산한다.

NPC 선택, 신분 카드 공개, 동일 인물의 반복 대화는
서로 다른 인물의 진술 수로 집계하지 않는다.

어떤 지식 카드와 공개 행위를 유효한 사건 관련
진술로 인정할지는 콘텐츠 담당자와 확정해야 한다.

공개 여부가 false인 경우 프론트는 모순 표시 버튼을
숨기거나 비활성화한다.

프론트의 수동 표시 가능 여부가 서버의 정보 접근
권한을 부여하는 것은 아니다.

## 11. 내부 데이터 구조 설계

현재 GameState.evidence는 증거의 stage를 저장한다.

현재 상태에는 명시적인 증거 최초 발견 Revision과
전체 타임라인 발견 순서가 저장되어 있지 않다.

새로운 발견 메타데이터가 필요하다.

내부 저장 모델 예시:

    TimelineDiscovery
      item_id
      source_kind
      source_id
      chapter
      discovery_order
      discovered_revision

GameState에 timeline_discoveries 기본값 빈 목록을
추가하는 방향을 우선 검토한다.

기존 SQLite의 JSON 상태 저장 구조를 재사용한다.

원본 관리자 타임라인 내용이나 민감한 문서 본문을
발견 이력에 중복 저장하지 않는다.

동일한 발견 항목의 중복 등록을 방지한다.

최종 데이터 모델 및 저장 방식은 실제 구현 단계에서
기존 저장소의 제약 조건을 확인하여 확정한다.

## 12. 발견 시점의 기록

다음 서버 처리 흐름에서 승인된 공개 항목을
발견 메타데이터에 반영한다.

- 현장 조사 증거 획득
- 기존 증거 수집 API
- NPC 대화 기반 증거 획득
- NPC 지식 카드 공개
- 승인된 추론 성립
- 승인된 스토리 정보 공개

단순 대화 요청이나 조회 요청에서는 새로운 발견
항목을 임의로 생성하지 않는다.

기존 commit_state 및 commit_turn의 트랜잭션을
재사용하는 방향으로 구현한다.

발견 Revision은 최종 저장되는 상태와 일치해야 한다.

원본 처리 실패 시 타임라인 메타데이터도
부분적으로 저장되어서는 안 된다.

## 13. 타임라인 조회 처리 흐름

    GET /timeline
          |
          v
    세션 소유권 검증
          |
          v
    콘텐츠 버전 및 현재 상태 조회
          |
          v
    세션별 발견 메타데이터 조회
          |
          v
    콘텐츠 승인 및 현재 접근 권한 재검증
          |
          v
    플레이어용 공개 문구 구성
          |
          v
    내부 식별자 및 비공개 정보 제거
          |
          v
    발견 순서 정렬
          |
          v
    상태 경쟁 여부 검증
          |
          v
    TimelineResponse 반환

조회는 읽기 전용으로 처리한다.

GET 요청에서 게임 상태, 점수, 플래그 또는
Revision을 변경하지 않는다.

## 14. 보안 및 스포일러 방지

- 관리자 타임라인을 API로 직접 반환하지 않는다.
- 기존 PolicyEvaluator 및 콘텐츠 승인 정책을 재사용한다.
- 현재 공개 가능한 문서와 진술만 사용한다.
- 비공개 sourceRefs 및 내부 정책 ID를 반환하지 않는다.
- 미공개 정보를 포함한 오류 메시지를 반환하지 않는다.
- 현재 세션에서 획득하지 않은 증거를 반환하지 않는다.
- 보호 증거의 별도 접근 규칙을 유지한다.
- 플레이어 노트 및 LLM 출력을 권한 근거로 사용하지 않는다.
- 다른 세션의 발견 정보를 조회할 수 없도록 한다.
- 조회 중 상태가 변경되면 일관되지 않은 응답을 방지한다.

초기 타임라인 구현에서는 E26 및 E30의 보호 내용을
일반 항목에 포함하지 않는 것을 우선 원칙으로 한다.

특수 보호 구획의 타임라인 공개가 필요한 경우
기존 별도 승인 정책과 공개 문구를 검토해야 한다.

타임라인 접근 자체는 보호 증거의 추가 열람 권한을
부여하지 않는다.

## 15. 오류 및 캐시 계약

| 상태 코드 | 조건 |
|---|---|
| 200 | 정상 조회 또는 빈 결과 |
| 404 | 세션 없음 또는 접근 권한 없음 |
| 409 | 조회 과정에서 상태 경쟁 발생 |
| 503 | 콘텐츠 또는 필수 서비스 구성 오류 |

성공 응답에 다음 캐시 정책을 적용한다.

    Cache-Control: private, no-store

세션별 타임라인이 공유 캐시에 저장되지 않도록 한다.

콘텐츠 승인 검증이 불가능한 경우 관리자 원본이나
미검증 데이터를 대신 반환하지 않는다.

## 16. 기존 저장 세션 호환성

기존 GameState에는 타임라인 발견 이력이 없다.

기존 저장 세션도 로딩할 수 있도록 신규 필드는
기본값을 제공하는 방향으로 설계한다.

이미 획득한 증거의 타임라인 항목은 승인된 공개
데이터가 확인된 경우에만 복원 대상으로 검토한다.

최초 발견 순서와 Revision이 확인되지 않는 경우
임의의 과거 값을 생성하지 않는다.

이 경우 discoveryOrder 및 discoveredRevision을
null로 처리할 수 있도록 한다.

발견 순서를 알 수 없는 항목의 표시 순서는
안정적인 공개 항목 ID 등을 사용하여 결정한다.

해당 순서는 실제 과거 발견 순서가 아님을 구분한다.

GET 요청을 통해 기존 데이터를 자동 마이그레이션
하거나 상태를 변경하지 않는다.

기존 콘텐츠 버전의 타임라인은 이번 확장판
계약에서 새로 제공한다고 보장하지 않는다.

## 17. 프론트엔드 연동 계약

변경 예상 파일:

- frontend/src/api/types.ts
- frontend/src/api/client.ts
- frontend/src/api/httpApi.ts
- frontend/src/screens/Timeline/Timeline.tsx
- frontend/src/store/noteStore.ts

현재 화면은 다음 항목 구조를 사용한다.

    interface TimelineItem {
      id: string
      time?: string
      text: string
      isNew?: boolean
    }

신규 API 응답을 기존 화면 모델로 변환한다.

    {
      id: item.id,
      time: item.timeLabel ?? undefined,
      text: item.description,
      isNew:
        item.discoveredRevision !== null &&
        item.discoveredRevision > lastSeenRevision
    }

위 변환은 화면 연동 예시이다.

실제 시각 순 정렬에는 occurredAt과 원본 시간
정보를 함께 고려하는 별도 정렬 처리가 필요하다.

현재 시각 문자열만 비교하는 정렬은 서로 다른
사건 날짜를 처리할 수 있도록 개선해야 한다.

수동 모순 표시의 로컬 저장 키는 세션 단위로
분리하거나 세션 전환 시 초기화하도록 검토한다.

현재 noteStore.clear는 새 게임 시작 시 기록을
초기화하는 기능을 제공한다.

이번 문서 작업에서는 프론트엔드 파일을 수정하지 않는다.

## 18. 화면 갱신 시점

다음 상태 변경 성공 이후 타임라인을 다시 조회한다.

- 현장 조사 성공
- 증거 획득 성공
- NPC 대화 성공
- 승인된 추론 제출 성공
- 챕터 전환
- 스토리 이벤트 확인
- 게임 재접속 및 새로고침

기존 GameResponse.events는 일회성 진행 알림이다.

타임라인 복원을 해당 이벤트 배열에만 의존하지 않는다.

신규 타임라인 응답의 Revision이 최신 게임 상태와
일치하는지 확인한다.

동시 요청으로 오래된 응답이 도착한 경우
최신 타임라인을 이전 상태로 덮어쓰지 않는다.
