## 2. 작업 배경

확장판에서는 최종 추리 항목의 재구성과 범인 지목을
서로 분리하여 처리한다.

기존 엔딩 판정 엔진은 5종의 엔딩을 지원한다.

이번 작업에서는 재구성 조건, 증거 독립성,
지목 횟수, 엔딩 공개 정책 및 영속 상태 복원을
실제 HTTP 요청 기반으로 검증한다.

또한 실제 확장판 실행 경로를 분석하여
정식 배포를 위한 준비 상태를 확인한다.

게임 상태를 사용하여 검증하였다.

테스트에서 사용하는 원장과 증거 조합은
실제 사건 정본에 대한 검증을 의미하지 않는다.

## 5. 최종 재구성 API

### 5.1 요청

    POST /api/games/{session_id}/reconstruction

요청 필드:

| 필드 | 자료형 | 설명 |
|---|---|---|
| expectedRevision | integer | 현재 게임 Revision |
| selections | object | 추리 항목별 증거 배열 |

### 5.2 재구성 항목

| 항목 | API 키 |
|---|---|
| 동기 | motive |
| 접근 | access |
| 시간 | timeline |
| 은폐 | coverup |

### 5.3 제출 조건

- 현재 챕터는 CH04여야 한다.
- 현재 게임 단계는 INVESTIGATION이어야 한다.
- 세 개 또는 네 개의 추리 항목을 제출한다.
- 각 항목에 증거 두 개 또는 세 개를 제출한다.
- 동일 항목 내 중복 증거를 허용하지 않는다.
- 실제 수집한 증거만 제출한다.
- 서버 전용 원장의 승인된 조합과 일치해야 한다.
- 각 항목의 추가 추론 조건을 충족해야 한다.
- 최소 세 항목의 증거 집합은 서로 독립적이어야 한다.

제출한 네 항목 중 하나라도 승인 조건을 충족하지
않으면 기존 엔진은 재구성을 승인하지 않는다.

최소 세 항목의 독립성 조건은 모든 제출 항목을
검증한 이후 평가한다.

### 5.4 응답

    {
      "accepted": true,
      "created": true,
      "revision": 15
    }

| 필드 | 설명 |
|---|---|
| accepted | 최종 재구성 검증 완료 상태 |
| created | 신규 재구성 검증 상태 생성 여부 |
| revision | 최종 게임 Revision |

accepted는 현재 상태에 최종 재구성 검증 플래그가
존재하는지를 나타낸다.

이미 재구성 검증을 완료한 상태에서는 신규 요청의
조합에 대한 독립적인 정오답 결과를 의미하지 않는다.

### 5.5 재구성 상태 관리

재구성 성공 시 서버 내부 검증 플래그를 기록한다.

재구성 성공 자체는 범인 지목 성공이나
게임 종료를 의미하지 않는다.

수집 점수, 획득 증거 및 지목 기회는 유지된다.

동일한 승인 조합의 재제출은 신규 검증 플래그를
중복 생성하지 않는다.

## 6. 증거 독립성 검증

네 개의 추리 항목 중 세 개를 선택하는
네 가지 조합을 각각 검증하였다.

| 조합 | 테스트 결과 |
|---|---|
| 동기 + 접근 + 시간 | 통과 |
| 동기 + 접근 + 은폐 | 통과 |
| 동기 + 시간 + 은폐 | 통과 |
| 접근 + 시간 + 은폐 | 통과 |

위 결과는 독립적인 증거 집합으로 구성한
테스트 전용 원장을 기준으로 한다.

실제 정본에서도 위 네 조합이 모두 유효하다고
간주하지 않는다.

승인된 증거 조합이라도 동일한 근거가 중복되어
세 개의 독립적인 증거 집합을 구성하지 못하면
최종 재구성 검증을 승인하지 않는다.

## 7. 범인 지목 API

    POST /api/games/{session_id}/accusations

요청 필드:

| 필드 | 설명 |
|---|---|
| suspectId | 지목할 NPC |
| expectedRevision | 현재 게임 Revision |

### 7.1 지목 가능 조건

확장판은 다음 조건을 모두 충족해야 한다.

- 전체 증거 개수의 50% 이상 수집
- 전체 가중치 점수의 50% 이상 확보
- 현재 지목 가능한 게임 단계
- 남은 지목 기회 존재
- 서버에서 공개한 NPC

수집 점수와 증거 개수는 서버가 계산한다.

프론트엔드는 서버의 canAccuse 응답을 사용한다.

### 7.2 지목 결과

| 결과 | 의미 |
|---|---|
| CORRECT | 올바른 범인 지목 |
| INCORRECT | 잘못된 범인 지목 |
| NOT_ENOUGH_EVIDENCE | 증거 부족 |

CORRECT는 범인 지목 결과이며 FULL 엔딩과
동일한 의미가 아니다.

최종 엔딩은 별도의 서버 판정 결과를 사용한다.

### 7.3 지목 기회 관리

초기 지목 기회는 세 번이다.

정상적인 지목 시도에서만 기회를 차감한다.

증거 부족으로 지목하지 못하는 경우에는
게임 상태와 지목 기회를 변경하지 않는다.

오답 이후 기회가 남아 있으면 조사 단계로 복귀한다.

세 번째 오답에서는 UNSOLVED 엔딩으로 종료된다.

이전 Revision을 사용하는 재요청은 HTTP 409로
차단하며 지목 기회를 중복 차감하지 않는다.

## 8. 수사 포기 API

    POST /api/games/{session_id}/give-up

요청:

    {
      "expectedRevision": 5
    }

응답:

    {
      "ending": "NO_EVIDENCE",
      "revision": 6
    }

확장판 조사 단계에서 지목 조건을 충족하지 못한
경우에 수사 포기가 가능하다.

수사 포기로 게임을 종료하더라도 지목 기회나
기존 수집 점수를 임의로 차감하지 않는다.

지목 조건을 이미 충족한 경우에는 기존 정책에
따라 수사 포기 요청을 거부한다.

## 11. 심화 엔딩 조건

기존 DEEP_EVIDENCE 및 DEEP_FLAGS 정책을 유지한다.

보호 증거 열람 동의와 실제 콘텐츠 공개 승인은
별개의 조건이다.

테스트에서는 심화 엔딩에 필요한 증거 또는
검증 플래그가 하나씩 누락된 상태를 구성하여
FULL로 판정되는 것을 확인하였다.

이번 신규 테스트는 E30 및 각 DEEP_FLAGS의
누락을 검증한다.

실제 E30 승인, 수집 및 심화 추론 플래그의
자연 생성까지 검증한 것은 아니다.

보호 증거의 조건을 우회하기 위한 운영 코드
변경은 수행하지 않았다.

## 12. 엔딩 조회 및 정보 공개

    GET /api/games/{session_id}/ending

게임이 종료되기 전에는 엔딩 조회를 차단한다.

| 엔딩 | truth 필드 |
|---|---|
| NO_EVIDENCE | null |
| UNSOLVED | null |
| ESTIMATED | null |
| FULL | 서버 검증 사실 제공 |
| DEEP | 서버 검증 사실 제공 |

FULL 및 DEEP에서만 범인과 사건 관련 정답 정보를
기존 엔딩 응답에 포함한다.

엔딩 정보의 공개 범위는 서버 판정 결과를 따른다.

다른 플레이어의 세션으로 엔딩 정보를 조회할 수 없다.

기존 엔딩 이미지 보호 API와 공개 정책은 유지한다.

## 17. 발견된 P0 결함

### 17.1 실제 확장판 판정 원장 연결 누락

기존 테스트는 app.state.case_truth에
ExpandedCaseTruth를 직접 등록한다.

그러나 실제 확장판 실행 진입점인
api/expanded_main.py 및 관련 초기화 모듈에서
확장판 판정 원장을 로딩하고 등록하는 코드가
확인되지 않았다.

실제 실행 환경에서 별도 원장 주입이 없다면
최종 재구성 및 범인 지목 요청이 실패할 수 있다.

### 17.2 영향 범위

| 기능 | 영향 |
|---|---|
| 최종 재구성 | 원장 미연결 시 HTTP 503 |
| 범인 지목 | 지목 조건 충족 후 원장 미연결 시 HTTP 503 |
| FULL 및 DEEP 조회 | 원장 미연결 시 HTTP 503 |
| 실제 최종 플레이 | 완료 여부 검증 필요 |
| 정식 배포 | 차단 결함으로 관리 |

증거 부족 상태에서의 지목 및 수사 포기는
별도의 조건으로 처리된다.

원장 미연결 시 모든 요청이 실패하는 것은 아니다.

### 17.3 검증 결과

test_day9_missing_truth_fails_closed에서
테스트용 판정 원장을 제거하여 장애를 재현하였다.

재구성 및 지목 요청은 HTTP 503을 반환하며
게임 상태와 지목 기회는 변경되지 않았다.

이는 보안상 안전한 실패 동작이나
정상 배포를 위한 기능 준비 완료를 의미하지 않는다.

### 17.4 후속 수정

별도의 P0 이슈를 생성하여 다음 작업을 수행한다.

- 최신 확장판 정본 분석
- 서버 전용 ExpandedCaseTruth 구성
- 승인된 추리 항목별 증거 조합 검증
- 콘텐츠 버전 및 릴리스 무결성 확인
- 실제 expanded_lifespan 초기화 연결
- 누락되거나 유효하지 않은 원장 처리
- 종료 시 원장 정리
- 정답 데이터 외부 노출 방지
- 실제 런타임 기반 통합 테스트
- 기존 콘텐츠 버전과의 분리 검증

기존 테스트용 범인 정보와 가상 증거 조합을
운영 판정 원장으로 사용하지 않는다.

## 18. 프론트엔드 연동 지침

최종 재구성의 accepted 및 created를 구분한다.

accepted가 true여도 게임은 즉시 종료되지 않는다.

범인 지목 결과와 실제 엔딩 코드도 구분한다.

최종 화면은 GET /ending의 서버 결과를 기준으로
표시한다.

게임 종료 여부는 서버 GameResponse.phase 및
최종 엔딩 응답으로 확인한다.

지목 기회는 서버 attemptsLeft를 사용한다.

HTTP 409 발생 시 최신 게임 상태를 조회한다.

HTTP 503 발생 시 정상 판정 성공으로 간주하지 않고
서버 준비 또는 장애 상태로 처리한다.
